# 配置与业务接入契约

## 可配置即可使用的交付

技能的产物是一个完整空白应用，而非 OAuth 示例片段。正常安装后展示授权状态和空白业务区域；授权后自动维护不依赖商家保持页面打开。开发阶段由本机 workerd 执行 Alarm，停止本机进程后不再承担持续维护；部署后由 Cloudflare 执行。

新应用将非敏感运行配置集中在 Wrangler 的默认环境与 `env.production`，不要要求用户修改多个源码常量。前端所需公开配置由后端从同一来源提供，或通过等效的受控构建注入。APP Secret 只属于后端。

| 配置 | 放置与含义 |
| --- | --- |
| Worker 名称 | `name` 和独立的生产 `name`；按用户指定的应用名称设置 |
| `APP_ENV` | `development` / `production`；用于环境检查 |
| `APP_URL` | 当前环境公开 HTTPS origin；无用户信息、路径、query、fragment；回调与通知地址由它派生 |
| `SHOPLINE_APP_KEY` | 当前环境 SHOPLINE 应用身份，与平台登记一致 |
| `SHOPLINE_APP_SECRET` | 开发用被忽略的 `.dev.vars`；生产使用目标 Worker 的远端 Secret |
| `SHOPLINE_SCOPES` | 平台已配置、实际需要的权限；规范化为集合比较 |
| `SHOPLINE_API_VERSION` | 明确选定并已核对的受支持 Admin/Webhook 版本；统一用于路径、订阅和事件契约 |
| 内嵌模式 | 与平台一致；使用显式配置或官方入口约定判定，并保留签名中的 `lang`；不得把任意 URL 参数当作登录证据 |
| 本地 HTTPS | 需要 Tunnel 时配置开发域名、Tunnel 名称和本机端口；从 `APP_URL` 派生 hostname，避免多处手填 |

这些字段名是建议的应用契约，可适应已有项目。不要为配置创建复杂通用框架。身份、域名、scope 或 Secret 未填写时，公开页面仍可提示如何配置；授权接口返回明确配置错误，不使用虚拟值向平台请求。诊断仅列出缺少的字段名，不回显密钥。

README 将用户准备工作集中为一张清单：

1. 在 SHOPLINE 创建或选择对应环境的应用，确定内嵌模式、权限和测试店铺。
2. 填写上述非敏感配置；通过本机文件或远端 Secret 输入 APP Secret，不将真实值放进示例或命令历史。
3. 以当前实现为准登记应用首页、OAuth 回调和通知地址。默认分别为 `APP_URL/`、`APP_URL/api/auth/callback`、`APP_URL/api/webhooks/app`；生命周期事件由应用调用订阅 API 维护，区分地址说明与需要在平台表单实际填写的字段。
4. 启动本机 HTTPS 联调，或在授权范围内执行生产部署；从 SHOPLINE 正常入口完成安装授权。

Webhook API 版本和授权依赖的 scope 须查官方文档，不能靠占位值宣称真实可用。配置完成不等于平台身份创建、域名可达、远端 Secret 已写入或店铺已授权，分别验证。

## 业务开发边界

授权层独立于业务模块。可采用以下职责划分；小项目允许合并文件，不强制框架：

```text
worker/index.ts           路由组合、导出 ShopAuth
worker/auth.ts            ShopAuth、会话鉴权、当前安装校验
worker/shopline.ts        受授权保护的服务端 SHOPLINE 请求
worker/business.ts        未来业务路由入口，初始为空
src/App.tsx               授权状态与应用外壳
src/pages/Home.tsx        可直接替换的空白业务页面
```

实现并记录两个服务端接口，名称可随项目调整：

- `requireShopSession(request, env)`：校验 Cookie、scope、安装状态和会话有效期，返回当前店铺及不透明的安装标识。调用方不能用 query/body 的 handle 切换店铺，业务模块不获取会话摘要或完整授权存储。
- `shoplineFetch(context, path, init)`：从授权服务取得当前有效令牌，校验 context 仍对应当前安装，再构造固定店铺的 SHOPLINE HTTPS 请求。拒绝绝对 URL、协议相对 URL及路径逃逸，不允许浏览器提供任意目标地址；保留超时、手动拒绝 3xx 和服务端错误分类。不提供公开通用代理接口。

令牌操作仍由 `ShopAuth` 按店铺协调。服务端内部 RPC 可以取得调用所需令牌，但不将它放进浏览器响应、Cookie、URL、日志或业务持久存储。授权服务是令牌的唯一持久来源。

每次重新授权生成可持久识别的安装标识或单调版本。业务上下文、未来异步任务和延迟网络响应绑定该标识；请求前检查当前安装，响应返回后在本地提交业务结果前再次核对。旧安装的 401 不能撤销新安装。卸载阻止后续调用和本地结果提交，无法撤回已发送到 SHOPLINE 的请求；不要声称原子取消了外部副作用。

SHOPLINE 明确要求重新授权的响应（含适用版本的 `X-SHOPLINE-API-Request-Failure-Reauthorize`）由授权层统一识别，并以安全错误返回前端。内嵌页面通过 App Bridge 从正常授权流程恢复，不循环重放旧 code。不把所有 403、限流、超时或 5xx 都当成卸载；不自动重放有副作用或结果不明的业务请求。

README 的接入示例只说明如何调用上述已实现接口、增加受保护路由和替换空白页面。鉴权失败返回 JSON 401；暂时无法核验返回 503；Cookie 认证的写接口检查 Origin 和内容类型。不为演示引入产品、订单、计费或写入真实店铺数据。

## 完成标准

- 核心授权功能没有待实现的存储、刷新、会话或撤销存根；业务空白区有明确扩展位置。
- 开发者不用改授权核心即可增加受保护业务接口、调用 SHOPLINE 和增加页面。
- 配置和平台地址一致，非敏感配置与密钥各有明确唯一来源。
- 本地、生产构建与部署命令已实现，未授权的远端操作不为验证而执行。
- README 明确实际通过的验证，以及仍待填写、登记、部署或真实店铺联调的事项。
